# MVVM 패턴 

$MVVM 패턴을 식당에 비유하면 다음과 같다.$ 

- **View (뷰) : 메뉴판, 테이블**
	- 손님은 메뉴판을 보고 음식을 고름(UI와 상호작용)
	- 완성된 음식을 테이블 위에서 받음. 
	- 메뉴판 자체는 요리를 하거나 재료가 어디 있는지 알지 못함.
	- **그냥 보여주고, 주문을 받는 역할** 
- **Model (모델) : 주방의 식자재 창고**
	- 요리에 필요한 모든 재료(데이터)가 보관됨.
	- 식자재는 스스로 요리가 되지 않고 메뉴판에 대해서도 전혀 모름
- **ViewModel (뷰모델) : 요리사**
	- 요리사는 `손님(View)`에게서 `주문(이벤트)`을 받으면, `창고(Model)` 에서 재료를 가져와 **먹기 좋게 요리(데이터가공)**, **접시에 담아(상태 관리)** 내놓음. 
	- 요리사는 메뉴판이 어떻게 생겼는지(UI 생김새)는 모르지만, '불고기' 주문이 들어오면 어떤 재료로 어떻게 요리해야 하는지는 알고있다. 

- 이처럼 각자의 역할이 명확히 분리되어 있어, 메뉴판 디자인이 바뀌어도 요리사의 레시피는 바뀔 필요가 없고, 식자재가 바뀌어도 손님은 똑같이 메뉴판으로 주문할 수 있다.

### Model - View - ViewModel 

1. **Model**
	- `역할` : 앱의 **데이터, 비즈니스 로직** 담당. 순수한 데이터와 그 데이터를 처리하는 로직의 집합 
	- `예시` : `Student`, `AttendanceRecord`같은 데이터 클래스(객체)
	- `특징` : View나 ViewModel에 대해 전혀 알지 못함. 
2. **View**
	- `역할` : 사용자에게 보여지는 **UI**담당. 입력을 받고, ViewModel의 데이터를 화면에 그리는 역할만 함. 
	- `예시` : Flutter의 `Widget`들 
	- `특징` : 최대한 **"멍청하게"** 만드는 것이 핵심. 스스로 데이터를 만들거나 복잡한 계산을 하지 않음. 오직 ViewModel이 **"이거 보여줘"** 라고 하면 보여주고, **"버튼 눌렸어"** 라고 ViewModel에게 알려줄 뿐이다. 
3. **ViewModel**
	- `역할` : **View와 ViewModel** 사이의 중재자. MVVM패턴의 핵심.
	- `주요 임무` : 
		1. `View를 위한 데이터 소유` : View가 화면에 표시해야 할 모든 **상태**를 가지고 있다. (`예 : List<Student> studentList, bool isLoading`)
		2. `View를 위한 로직 제공` : View로부터 "저장 버튼 눌렸어" 같은 요청을 받으면 Model을 이용해 데이터를 저장하는 등 **실제 행동을 처리하는 로직을 담고 있다. 
		3. `데이터 가공` : Model로부터 가져온 순수한 데이터를 View가 보여주기 쉬운 형태로 가공(`예 : DateTime 객체를 '2025년 8월 19일' 같은 형태로 변환`)
	- `가장 중요한 특징` : ViewModel은 Model에 대해서는 알지만 **View**에 대해서는 전혀 모른다. 

#### Why MVVM 패턴?
1. **테스트 용이성**
	- ViewModel은 UI 코드를 전혀 포함하지 않기 때문에, 화면을 직접 띄우지 않고도 모든 UI 로직(버튼 클릭 시 동작 등)을 자동화된 코드로 쉽게 테스트 할 수 있다. 
2. **관심사 분리**
	- UI를 그리는 코드와 실제 로직이 분리되어 코드가 훨씬 깨끗하고 이해하기 쉬워짐. 
3. **유지보수 용이성**
	- 나중에 버튼의 색깔, 위치를 바꾸고 싶으면 View만 수정, 저장 로직을 바꾸려면 ViewModel만 수정. 서로 영향을 안 주어 수정이 쉽고 안전.
